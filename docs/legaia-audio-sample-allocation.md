# Audio sample allocation foundation

The importer can now encode a different number of complete PCM blocks into a qualified non-repeating SPU sample, repack its VAB/carrier and allocate the complete physical PROT owner. **This is a prerequisite checkpoint, not a completed editor feature.** [Retained allocation input review/retention and history/Save/Open](legaia-audio-allocation-inputs.md) are now implemented as the next metadata milestone. [Native allocation backend commands, dynamic Current composition/PCM and normal Build](legaia-audio-native-allocation.md) are now qualified. Editor controls and older Current authoring interoperability remain pending. Existing editor WAV imports continue to use their fixed-frame contract.

`importer.audio_sample_allocation.allocate_sample_wav` accepts freshly hashed Retail and Current sample bytes plus a bounded mono signed16 RIFF/WAVE input. A separate `read_allocation_pcm_wav` contract allows 1–4096 complete 28-frame blocks; the existing `read_pcm_wav` still requires the exact qualified frame count. There is no implicit padding, truncation or resampling. Input rate is metadata only. Exhaustive predictor/shift encoding uses the existing closed-loop integer codec, reports lossy errors and reopens decoded PCM independently of the encoding decisions.

Allocation requires an encoded final flag of 1. Before it, only flags 0 and 4 are allowed. Retail non-repeating samples often have flag 4 at block 1: every such start marker keeps its exact original block ordinal. Inputs ending at or before any marker are refused, rather than moving a marker or combining it with the end flag. Current must retain the same marker ordinals. Sustain/repeat flags, unknown operands, incomplete prefixes, exhausted prefixes without encoded ends and decoder-budget exhaustion are refused. The opaque source tail after the encoded end is retained byte-for-byte. This qualification describes encoded bytes; it does not establish driver playback policy or hardware behavior.

`repack_audio_samples` reconstructs the pool in stable sample ordinal order from a freshly hashed effective carrier. A batch may replace up to 32 selected samples. It updates the VAB size word at +12 and the selected one-indexed u16 sample sizes in eight-byte units. Sample counts, reserved size-table spacer/unused words, program/tone tables, unselected samples and the bank tail stay held. New sample positions are reconstructed from the new table; old byte offsets are never reused against the grown pool.

Three native carriers are supported: standalone VAB, a leading contiguous type-0 VAB chunk, and split type-0 header/type-1 sample chunks. A split allocation requires the first piece to end exactly after the complete header/tables. Chunk lengths are updated on their four-byte native boundary. Contiguous in-chunk opaque bytes and all following SEQ/other carrier bytes remain exact. No interior signature search or guessed split is used. `allocate_audio_sample_wav` binds Retail/Current carrier hashes, source bank, sample ordinal and both sample hashes before using the codec and repacker. Other effective bank/sequence/sample edits are carried through unchanged.

`importer.audio_bank_growth.rebuild_audio_bank_entry` uses uniquely owned consecutive physical starts. Growth is padded to whole sectors and relocates later starts through the existing PROT writer. Sample/carrier shrinking retains the old physical allocation and appends zero padding; the archive never shrinks. Shared resource composition accepts an exclusive `audio-sample-bank` request with `entry_index`, `expected_entry_sha256` and complete `candidate` bytes. Fixed edits in that same physical owner must already be included in the candidate; overlapping independent patches and competing resource owners are refused. Final composition reopens the complete candidate and padding. Other resource kinds retain their existing request/audit contracts.
